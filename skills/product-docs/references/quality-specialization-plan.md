## 2. 目标与结构建议

让质量链路从用户需求延伸到架构、设计、代码和验证，最后回到真实用户结果。
保留 `product-docs` 为总入口，新增三个专业 Skill；不另建 `project` 路由。

| Skill | 守护对象 | 主要输入 | 主要输出与质量证据 |
| --- | --- | --- | --- |
| `product-docs`（已有） | 用户意图、PRD、可观察行为、最终验收、文档权威与交付状态 | 用户目标、约束、当前产品权威、真实使用反馈 | 明确需求与验收、必要的专业路由、声明与证据映射、剩余缺口 |
| `architecture`（架构工程） | 技术选型、模块及数据边界、接口、非功能指标、测试策略与架构 Review | 需求、验收、现有架构、实测路线与约束 | 决策依据、契约与不变量、分层测试及 Case 矩阵、项目质量阈值、功能单元验收结论 |
| `code-quality`（代码质量） | 函数与变量、ctx、错误及资源、数据细节、单测和代码 Review | 已采用的架构契约、适用的设计规范、代码与变更范围、项目规范、测试策略 | 实现产物、风险路径单测、静态检查、Review 问题及修复证据、返回上层的交付结果 |
| `design-standards`（中文：设计规范） | 情绪板到标准库、模板、自检和精修的可复用设计闭环 | 产品目标、受众、使用场景、品牌和媒介约束、已有设计系统 | 设计原则、版本化标准库与模板、实际渲染的检查及精修证据 |

三层工程质量体系仍是需求与验收、架构与工程、代码质量。设计规范是与工程
专业协作的领域能力，不应硬塞进代码层，也不成为第二个产品需求权威。

设计属于产品工作中的专业领域；独立 Skill 的理由是它有独立的方法、产物、
复用方式及验收证据。设计决定体验如何表达和验证，产品入口守护为什么做、
为谁做，以及是否满足用户目标。设计规范也可以服务海报、文档或演示等独立
任务；这些任务不必虚构软件架构或强制走完整产品链路。

保持产品入口的理由：当前已有链路、权威和治理能力可复用；另建 `project`
容易重复维护范围、进度、验收和路由。专业 Skill 可直接使用，只读取必要
上游约束；总入口并不意味着所有任务都要重跑全部 Skill。

### 2.1 四个相连的交付闭环（用户明确要求）

每层都承担“接收上游目标 → 形成本层约束和验收标准 → 向下交付 → 收回结果
→ 按本层标准验证 → 返回上层结论与证据”。仅把任务转给下游不能完成闭环。

| 层 | 向下交付什么 | 收回什么、由本层验证什么 | 向上返回什么 |
| --- | --- | --- | --- |
| 产品 `product-docs` | 用户需求、PRD、范围、优先级、产品验收标准及必要的设计/架构任务 | 设计和架构闭环结果、实际产品行为；核对端到端真实路径和整体用户目标，不以专业局部通过代替整体交付 | 向用户交付整体结果、证据、限制和剩余验收事项；用户保有最终接受权 |
| 设计 `design-standards`（按需） | 已采用的设计原则、标准库、模板和视觉验收要求，指导架构及代码落实 | 实际渲染/实屏与适用状态；检查视觉一致性及适用的响应式、可读性、交互反馈和无障碍要求，驱动精修复查 | 向产品返回设计与视觉验收结论、证据及缺口；向相关实施方反馈具体修正要求 |
| 架构 `architecture` | 技术选型、功能单元划分、接口、数据契约、非功能指标、测试策略和单元级交付标准 | 实现、Review 和测试证据；验证功能单元行为、单元间集成、接口/数据一致性及适用非功能指标 | 向产品返回架构与功能单元验收结论、集成证据及缺口；设计受影响时同步相应结果 |
| 代码 `code-quality` | 接收上游结构与规范，拆解并执行代码实现、Review、测试及问题修复，不另造产品或架构要求 | 收回并核对实现、Review 和测试结果；完成代码级修复及复测，确认交付符合接收的契约 | 向架构返回实现和质量证据；有设计时向设计返回实际视觉产物、状态和证据，保留失败、跳过和缺口 |

软件产品的主要下发与回收关系：

```text
产品 ─需求/产品验收─→ 架构 ─结构/功能单元契约─→ 代码
产品 ←整体功能证据── 架构 ←实现/Review/测试──── 代码

有设计时增加：
产品 ─体验目标─→ 设计 ─规范/模板─→ 架构及代码
产品 ←视觉结论── 设计 ←实际产物─── 代码（及相关架构结果）
```

这不是强制“产品 → 设计 → 架构 → 代码”的单一串行流程。设计和架构围绕
同一产品目标协同：设计要求可影响接口及实现，技术限制可反馈设计；正式改变
产品范围或验收含义时返回产品层处理。无设计任务时跳过设计闭环。

上层接收下游结果后必须核对本层标准及证据充分性，不能直接转抄“通过”。
代码测试通过不等于功能单元通过；功能单元通过不等于视觉通过；各专业通过
也不等于整体产品验收和用户接受。验证可复用足够的现有证据，不机械重跑全部
检查。发现缺口时返回负责该缺口的层修复并复查，闭环完成后再向上返回。

### 2.2 最小下发与返回契约（Agent 落地建议）

优先引用项目已有文档、标识与证据，不创建跨模块协议、独立仓库或正式交接包。

- 下发：目标与范围、输入及采用的契约/规范版本、允许变更边界、验收标准、
  所需证据。只有发生实质变化才更新这些信息。
- 返回：交付产物与适用的构建/输入身份、逐项验收结果、Review/测试证据、
  未解决问题和限制，以及需要上层决定的偏差。
- 收回验证：确认结果对应本次范围和版本，证据证明的是本层声明；明确通过、
  失败、部分完成、跳过或阻塞，不能把缺证据解释为通过。
- 回退修复：错误代码回代码层，契约或集成问题回架构层，视觉规范或表达问题
  回设计层，用户目标或验收冲突回产品层；跨层影响同步真实受影响的契约。

## 3. 薄入口职责

产品 Skill 仅在专业路由段落接通入口，不改现有恢复规则、需求权威、前置描述
或 UI 元数据。专业能力的共通契约及细则由各自 Skill 拥有。

1. 按实际影响范围选择专业职责：架构/接口/测试策略，代码实现/单测/Review，
   或设计系统/模板/视觉质量。局部措辞、状态更新不自动触发专业全链审计。
2. 调用前检查专业 Skill 是否真实存在、可读且适用。三个 Skill 已在本次环境
   落盘；其他环境仍须按名称发现，不能声称不存在的能力已调用或门禁已通过。
3. 将必要目标、验收、现有边界和变更范围交给专业环节；要求各层完成本层
   下发—收回—验证—返回闭环。产品层收回并验证整体交付，不把下游细则
   复制进 `product-docs`，不以路由结束代替交付完成。
4. 专业能力缺失时如实报告缺口，在现有授权范围内使用已有适用手段；若
   必须满足的质量门禁无法验证，就不能声明它已通过。缺失不自动授权安装、
   创建 Skill 或扩大工作范围。
5. 此计划仅在规划或实施专业扩展时按需读取，不成为每次产品工作的必读项。

## 4. 架构工程：前期分析依据（初版已落实，正式规则见对应 Skill）

技术选型说明解决什么验收目标、依据哪些真实约束、有哪些可行替代方案和
取舍。沿用现有有效架构，只有真实边界或证据要求才拆服务、模块或协议。

架构契约要覆盖所有权、允许的读写方、输入输出、错误边界、数据不变量和
恢复能力。第三方服务、登录权限、限流及可获得内容属于真实依赖约束，不能
由 mock 或工具名称代替验证。

测试策略区分产品验收 Case 与工程 Test Case；根据风险配置单元、集成、
契约、端到端及真实授权路径验证。性能、可靠性、安全、可观测性和恢复指标
仅在适用时定义，并给出可测阈值、测量环境和失败条件。

覆盖率需明确统计对象、关键路径、排除项和项目阈值；不得臆造统一百分比。
覆盖率不能代替断言质量或真实路径。架构 Review 检查契约与验收的连接、
遗漏及可恢复性，明确哪些缺口阻断进入下一阶段，哪些属于已接受的限制。

实现返回后由架构层按下发契约完成功能单元与集成验收，汇总足够的工程证据
返回产品层。单元测试属于代码证据，不能独自证明整个功能单元或集成成立。

## 5. 代码质量：前期分析依据（初版已落实，正式规则见对应 Skill）

从架构契约落到可审查代码和测试，不要求为每一行都制造说明文档。

- 函数和命名：职责、输入输出、副作用、复杂度与边界；按语言及项目采用
  适用规范，公开契约和关键函数必须可解释、可验证。
- ctx：先判断它指取消上下文、请求上下文还是 Agent 上下文；分别控制
  生命周期、作用域、传递、取消/超时，或来源、体积、隔离和恢复，不混为一谈。
- 错误与资源：错误传播、重试条件、幂等、清理、并发与取消路径。
- 数据：不变量、空值、边界、权限、编码和不可逆变换；完整性声明有相应证据。
- Unit Test：按关键行为与风险覆盖正常、异常、边界、取消/超时、重试及并发；
  不强制每个无逻辑函数都有镜像测试，不用通过数代替验证价值。
- 工程检查：沿用项目的 lint、类型检查、静态分析与测试门禁；mutation test
  等作为风险适用选项。Review 记录实质问题、阻断条件和修复验证。

语言、框架细则按需进入 supporting references；共享入口只保存共通契约，
不把所有语言规范压成一份无法执行的大清单。

本层接收产品、架构及适用设计约束，执行实现、Review、测试、修复和复测，
最后返回符合接收契约的产物及证据。局部测试或 Review 完成不越权改写上层
验收标准，也不替代架构功能验收、设计视觉验收或产品最终交付。

## 6. 设计规范：前期分析依据（初版已落实，正式规则见对应 Skill）

建议闭环：情绪板 → 设计原则 → 标准库 → 模板 → 自检 → 精修 → 版本化复用。
已有有效标准时可从标准库或模板进入，不必每次重新制作情绪板。

| 环节 | 必须解决的问题 | 形成的产物或证据 |
| --- | --- | --- |
| 情绪板 | 受众、场景、情绪与参考方向是什么？ | 标明来源和候选状态的探索材料，不能自动升级为规范 |
| 设计原则 | 采用哪些方向，依据什么目标？ | 可判断的原则、适用范围及明确采用的方向 |
| 标准库 | 如何保持一致并支持实际媒介？ | 色彩、字体、间距、布局及适用的组件状态、动效、无障碍规则 |
| 模板 | 哪些结构可复用，哪些内容可变？ | 模板约束、示例和允许变化的范围；软件场景连接 Token/组件实现 |
| 自检 | 实际产物是否符合目标和标准？ | 渲染或实屏证据，检查布局、可读性、内容、状态及适用的响应式行为 |
| 精修 | 发现的问题是否被修复并验证？ | 问题清单、修改和复查证据，保留尚未解决的限制 |
| 版本化复用 | 后续如何采用、升级或回退？ | 已采用的标准版本、模板/组件依赖及变更影响 |

视觉规范符合不等于可用性通过；可用性通过也不等于用户最终接受。产品任务
的设计验收仍连接产品验收，独立设计任务则连接其自身目标与验收。

规范下发后必须收回实际产物完成视觉验收与精修复查，再把结论返回产品层；
标准库和模板已经存在、或已经发给代码层，都不能证明该次设计交付闭环完成。

| 经验 | 通用约束 | 主责与验证重点 |
| --- | --- | --- |
| 下载器成功或页面元数据不能证明拿到了完整视频 | 验收检查实际产物、权限和完整性；工程成功与用户结果分开 | 产品入口定义完整性；工程验证真实授权路径与媒体实体 |

| C0/C1/C2、派生视图和备份具有不同所有权及恢复边界 | 来源、派生、记录、发布与运行状态分开；按实际范围验证完整性与恢复 | 架构定义契约；代码验证哈希、引用、重建等适用不变量 |
| 旧主对话、新主对话和重新采集可能身份变化 | 来源身份、版本、去重和幂等不能凭名称或旧 ID 推断 | 架构定义身份；代码验证变化、缺失及重复采集路径 |
| 某些材料明确要求停在 C0 | 阶段跳过是合法结果，不能为了全链完成擅自继续处理 | 产品保存范围；工程/代码证明跳过不会错误触发下游 |
| 恢复不能因摘要不完整而重启已完成任务 | unknown 不等于 unfinished，显式恢复条件与终态回放禁止要保持 | 现有产品生命周期契约继续拥有此规则，不在三个新 Skill 重复造状态机 |
| 工程通过、真实结果、用户接受和运行收口容易混淆 | 分开状态与证据阈值；运行记录不升级为需求或规范 | 产品入口及各专业结果共同保持声明边界 |

## 8. 前期实施顺序与验收依据（历史计划）

下列顺序是实施前建议；本轮用户已明确授权建立初版，文件及检查结果见 §10。
真实项目中的独立行为验证仍待实际任务，不自动启动新项目。正式专业规则已
放到实际 Skill，以下分析仅保留方案依据，不作为第二份可编辑执行权威。

1. **落实闭环契约。** 名称及用户要求的分层闭环已落盘，后续将最小输入、
   输出、适用范围、收回验证、失败回退、门禁及缺失处理落实到专业 Skill。
   验收：职责无重复，各层有实际回收验证责任，局部任务可独立执行。
2. **实现架构工程。** 先把需求/验收与技术契约、测试策略、Review 连接。
   验收：能解释选型与指标，能区分 fixture、工程门禁及真实路径，能发现
   关键测试缺口和明确失败条件。
3. **实现代码质量。** 从契约下沉到函数、ctx、数据、单测和代码 Review。
   验收：能识别实际实现缺陷和薄弱断言，采用项目适用标准，避免逐行文档化
   和对可逆低影响修改无差别加测试。
4. **实现设计规范。** 在真实视觉任务中跑通探索、采用、模板、渲染检查和
   精修闭环。验收：能区分候选与正式规范、定位视觉/使用问题并用复查证明
   改善，产物可按标准版本复用。
5. **联合回验并收敛入口。** 用有代表性的真实情境验证三层质量链和设计分支，
   检查缺失 Skill、专业直接调用、局部小改动、跳过路径和未通过门禁等情境。
   验收：每层下发、收回、验证、返回均能成立，失败能返回正确层修复；
   产品层独立判断整体证据是否充分。不漏掉用户目标，不夸大证据，不强制
   所有任务串行跑满四个 Skill，不改变已有授权或恢复边界。

主要风险：总入口膨胀、专业职责重复、指标机械化、规划能力冒充可用能力、
历史试点绑定通用规则。控制方法是条件入口、单一权威、项目适用阈值、可用性
检查、真实情境验证及只修复已观察到的缺口。
